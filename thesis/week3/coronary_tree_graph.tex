\section*{The coronary tree graph}

Turning a coronary centerline into a tree lets branching pattern, bifurcation angle, tortuosity and
dominance be read off one structure instead of each being re-derived separately. This note covers
how that tree was built and checked; the bifurcation angle built on top of it is covered elsewhere.

Kit delivered the centerline for each case, one per side, already built from the hand-corrected
mask (ground truth in the usual sense): skeletonized to a one-voxel line and Gaussian-smoothed
($\sigma = 0.5$\,mm) \cite{bransby2026imagecasx}, no segmentation network involved, with segment
names (LM, LAD, \ldots) carried over from the discarded hand traces by nearest-point matching. What
arrived was raw VTK geometry, not a tree: points and polylines with a per-point name. Before I
could read off branching pattern, angle or tortuosity, that geometry first had to become a rooted
structure, which the rest of this note covers.

\subsection*{Building the tree}

That per-point name is not enough to make a tree. A centerline file stores points and polylines,
short chains between consecutive points, with no encoded direction and no record of which
polylines share a vessel: a vessel is often split across several, usually wherever a side branch
leaves it. The name doesn't resolve either problem, since it labels a point, not a connection or a
direction: two polylines with the same name aren't thereby one vessel rather than, say, the trunk
and an unrelated sub-branch inheriting that name past an unnamed split (456 such splits occur in
the cohort). It is least reliable where it matters most, too: a junction point carries only the
parent vessel's label, so reading it off directly would misplace the points deciding where one
vessel ends and the next begins. Direction is a further fact no label supplies, fixed only once a
root is chosen and the tree walked outward from it.

\texttt{topology/graph.py} resolves connectivity and direction from the polylines and a chosen root
before using the names at all: it roots each side at its ostium, orients every polyline outward,
and merges one vessel's polylines into a single segment. Only then is a segment named, by majority
vote over its interior points, excluding the two endpoints since they carry the parent's label.
\Cref{fig:week3-tree-case1} shows one case: the centerline in space (left) and the same tree as a
dendrogram (right), height being distance from the ostium, so branch order and segment length read
off directly rather than estimated from the 3D view.

\subsection*{Checking the tree}

This tree was checked two ways. First, its connectivity against the branch-point and end-point
flags the dataset ships, defined independently via \texttt{scripts/survey\_topology.py}: across all
1600 sides it matches exactly (not fully independent, since the flags follow the same degree rule,
but it confirms the tree was recovered correctly). 1584 of 1600 sides form one clean rooted tree;
the other 16 are real anatomy or data defects, kept and flagged rather than dropped: 11 left sides
have two ostia, the absent-left-main variant where LAD and LCx arise separately and carry no LM
label; 2 left sides (84, 272) are a genuinely detached fragment, rooted at whichever endpoint sits
nearest the main tree, the closest justifiable stand-in for an ostium; 3 sides (8 left, 455 right,
776 left) contain a cycle, which a coronary tree cannot have, so the cycle-closing edge is dropped
and the drop recorded rather than silent.

Second, whether the tree's points are still the delivered centerline's own, not a redrawn
approximation. A \texttt{Segment}'s points are a direct slice of the raw array; building the tree
only decides which slice belongs to which segment and which way is outward, never resampling or
smoothing. A bifurcation is no exception: the junction point is the same array entry read into
every segment that meets there, not double-counted when segments chain into a vessel, but not
discarded either. \Cref{tab:week3-junction-points} lists the LAD segment's last two points running
into the D1 origin (case 1, left); the second, to machine precision, is also the first point of the
continuing LAD segment and of the D1 branch.

\subsection*{Extending to Herlev--{\O}sterbro}

None of the inputs above exist there: no corrected mask, no delivered centerline, no ostium, no
segment names. The mask instead comes from the segmentation network's prediction, skeletonized the
same way (Lee et al.\ 1994, the method ImageCAS-X itself cites) and Gaussian-smoothed at
$\sigma = 0.5$\,mm, feeding \texttt{graph.build\_tree} unchanged; the ostium comes from a
TotalSegmentator aorta \cite{wasserthal2023totalsegmentator}; segment names have no answer yet,
beyond training on the 14 labels directly instead of vessel-vs-background. Before a real
Herlev--{\O}sterbro scan, the plan is to run the same pipeline on the 160 ImageCAS-X test cases and
measure how far angles drift with a predicted mask instead of the corrected one: that drift is the
error this step adds, and it needs to be small next to how much the angle varies between people.
