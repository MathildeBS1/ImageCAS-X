\section*{The coronary tree graph}

Turning a coronary centerline into a tree lets branching pattern, bifurcation angle, tortuosity and
dominance be read off one structure instead of each being re-derived separately.

Kit delivered the centerline for each case, one per side, already built from the hand-corrected
mask (ground truth in the usual sense): skeletonized to a one-voxel line and Gaussian-smoothed
($\sigma = 0.5$\,mm) \cite{bransby2026imagecasx}, no segmentation network involved, with segment
names (LM, LAD, \ldots) carried over from the discarded hand traces by nearest-point matching. What
arrived was raw VTK geometry, not a tree: points and polylines with a per-point name, no encoded
direction and no record of which polylines share a vessel.

That file gives three things: points in 3D, which points connect to which (short polylines between
them), and which artery each point belongs to. None of the three settles where one vessel ends and
the next begins. A junction point's name is the parent vessel's, not the daughter's, so name alone
misplaces exactly the boundary that matters; and a vessel is often split across several polylines
wherever the skeletonizer happened to break the chain, not only at real branch points, so
connectivity alone gives adjacency, not vessel identity or direction.

\texttt{topology/graph.py} resolves connectivity and direction first, from the points and polylines
alone, before touching a name: it roots each side at its ostium, orients every polyline outward, and
merges one vessel's polylines into a single segment. Only then is each segment named, by majority
vote over its own interior points. What the tree adds, that the file alone did not have, is
structure: every point is now either an ostium, a bifurcation or a terminus, or lies on one directed
segment running between two of those, each segment with a known length, direction and name.
Branching pattern, bifurcation angle, tortuosity and dominance are all read directly off that
structure, not re-derived per case. \Cref{fig:week3-tree-case1} shows one case: the centerline in
space and the same tree as a dendrogram, height being distance from the ostium.

Checked against the branch-point and end-point flags the dataset ships
(\texttt{scripts/survey\_topology.py}): matches across all 1600 sides. 1584 of 1600 sides form one
clean rooted tree; the other 16 are real anatomy or data defects, kept and flagged rather than
dropped: 11 left sides have two ostia, the absent-left-main variant where LAD and LCx arise
separately; 2 left sides are a detached fragment, rooted at the endpoint nearest the main tree; 3
sides contain a cycle, which a coronary tree cannot have, so the cycle-closing edge is dropped and
recorded.

\subsection*{Extending to Herlev--{\O}sterbro}

None of the inputs above exist there: no corrected mask, no delivered centerline, no ostium, no
segment names. The mask instead comes from the segmentation network's prediction, skeletonized the
same way (Lee et al.\ 1994, the method ImageCAS-X itself cites) and Gaussian-smoothed at
$\sigma = 0.5$\,mm, feeding \texttt{graph.build\_tree} unchanged; the ostium comes from a
TotalSegmentator aorta \cite{wasserthal2023totalsegmentator}; segment names have no answer yet. The
plan is to run the same pipeline on the 160 ImageCAS-X test cases and measure how far angles drift
with a predicted mask instead of the corrected one, since that drift is the error this step adds.
